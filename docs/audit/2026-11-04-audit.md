# tula — P(-1) Audit: hardening, optimization, repair (2026-11-04)

**Scope**: tula 1.1.1 → 1.1.2 on cyrius 6.7.18 + sigil 3.13.15. Reviewed every
`src/*.cyr` module, the test suites, the fuzz and bench harnesses and the
consumer example, plus the stdlib calls tula leans on (`alloc`, `memcpy`,
`streq`, `file_read_all`, `mmap_file_ro`, `xlseek`). The prior audit is
[2026-07-01](2026-07-01-audit.md); its threat model stands (`SECURITY.md`).

**Method** (the P(-1) loop): baseline tests + benchmarks → cleanliness gates
(`fmt`, `lint`, `vet`, `deny`, `doc --check`) → internal review → **a probe
program per suspected defect, run against the unchanged 1.1.1 code**, so each
finding below is a reproduced failure, not a reading → external comparison
(safetensors, GGUF) → fixes + regression tests (mutation-checked) → post-review
benchmarks → a byte-for-byte differential against 1.1.1.

**Verdict: PASS after repair.** Ten defects reproduced, all fixed in 1.1.2,
none needing an API or format change. The worst was **F-2**: the mmap reader
accepted a truncated file, and the first read of its missing tail killed the
process with SIGBUS. The 2026-07-01 audit's guarantees held for **in-memory**
buffers, but both **file** readers trusted the length the header claimed.
Issues that need new API or a format decision are deferred to the roadmap
(§5).

---

## 1. Findings (all reproduced on 1.1.1, all fixed in 1.1.2)

| ID | Sev | Where | Defect (as reproduced) | Fix |
|---|---|---|---|---|
| F-2 | **High** | `tula_open_mmap` | A file shorter than its header's total was mapped and **validated as sound** (validation checked the header's own length). The first payload read past EOF raised **SIGBUS** (exit 135). A partial write, a truncated download or a hostile file could crash any mmap consumer. | Both readers compare the declared total with the real size (`lseek` to `SEEK_END`) **before** mapping. Shorter files are rejected. |
| F-3 | Med | `tula_open_mmap` | A file that mapped but then failed validation was **never unmapped**: 500 rejected opens left +500 mappings. Linux caps a process at ~65,530 maps, and the stdlib `alloc` itself uses `mmap`, so scanning enough hostile files would make **allocation fail process-wide**. | Unmap on validation failure. |
| F-4 | Med | `tula_read_file` | The heap reader sized its allocation from the header before knowing the file held that much. A **64-byte** file claiming 256 MiB reserved 256 MiB+ that the bump allocator never releases: 8 reads grew VmSize 256 MiB → 4,352 MiB. The cap was 2 GiB per file (`ALLOC_MAX`), so the amplification was ~3×10⁷. It also opened the path twice (header, then body). | Same real-size check before `alloc`. One `open`: header and body come from the same fd. |
| F-5 | Med | `tula_builder_add` | A negative `data_len` was accepted. `tula_align8(-100) = -88` moved the next tensor's `data_off` to **−88**, and `tula_serialize` copied it **over the manifest**. Writer-side, but it corrupts memory and writes a corrupt file. | Returns `TULA_ERR_BOUNDS`; builder unchanged. |
| F-6 | Low | `tula_builder_add` | `ndim ∉ [0, 8]` and payloads over `TULA_READ_MAX_BYTES` were accepted, producing files **tula's own reader rejects** (`validate` → `TULA_ERR_NDIM`). | Returns `TULA_ERR_NDIM` / `TULA_ERR_TOO_BIG` (per tensor and cumulative). |
| F-7 | Low | `tula_serialize`, `tula_builder_finish_signed` | `alloc` failure was unchecked, so the first `store64(0, …)` was a **SIGSEGV**. Reachable by any builder over 2 GiB (the stdlib `ALLOC_MAX`). | Return 0. |
| F-8 | Low | `tula_nf4_blocks` / `_pack` / `_unpack` | `block <= 0` **divided by zero** (SIGFPE, exit 136). A consumer deriving `block` from a file's shapes could hit it. | Return 0 and write nothing. |
| F-9 | Low | `tula_entry_payload_ok` | Its documented contract says a negative dim returns 0, but shape `[0, -5]` returned **1** (the scan returned at the zero). `[2³⁰, 2³⁰, 0]` (an empty tensor) returned 0 via the overflow guard. | Every dim checked for sign first. Any zero dim then returns 1, before the product. |
| F-10 | Low | `tula_close_mmap` | `tula_close_mmap(0)`, i.e. closing a failed open, read the header at address 0: **SIGSEGV**. | No-op for 0. |
| F-11 | Low (defensive) | `tula_serialize` | The 0–7 alignment padding bytes after each tensor, and the reserved signature block, were never written, so file bytes depended on what the allocator returned. Not reachable today: the stdlib allocator zeroes memory before reuse (CVE-2026-34988 class fix). | Written explicitly as zero. Output is a pure function of the builder (tested deterministic). |

Also repaired (no defect in the codec itself):

- **Reference consumer** (`examples/consumer.cyr`, the v1.0 CI gate) kept going after
  a failed check and then dereferenced what the check guarded: a missing tensor's 0
  entry, an unchecked scale sidecar. It now rejects on every failed check, guards
  the scale and bias with `tula_entry_payload_ok`, and checks rank, dims and dtype
  against what it expects before they size anything.
- **Fixed `/tmp` names** in the tests and the example (a pre-planted symlink is
  followed by `O_TRUNC`; parallel runs collide) moved to `build/` (gitignored).
  `make test` now creates it.
- **`cyrius doc --check`**: 8 public accessors had no doc comment; now 0.

## 2. Verification

- **Tests 105 → 178** (6 suites). New `builder.tcyr` (38): the writer contract
  and `tula_find`. `fileio.tcyr` +14: truncation, an over-claiming header,
  trailing bytes still opening, no mapping left after 200 rejected opens, a
  directory, `close_mmap(0)`. `dtype.tcyr` +21: differential tests of every
  optimized helper against the 1.1.1 implementation, `block ≤ 0`, the
  `payload_ok` dim cases.
- **Mutation check.** Breaking `tula_find`'s NUL comparison, the ternary decode,
  or the NF4 block scale each turns a suite red. One mutant survived: NF4
  nearest stopping on a *tie* rather than a strict increase. It is equivalent
  on every input tried, because a tie can only occur once the scan is already
  past the minimum. The shipped strict `>` is the conservative choice.
- **Fuzz harness, strengthened.** Every buffer under test now ends at a
  `PROT_NONE` guard page, so an over-read by the validator, an accessor,
  `tula_verify` or an unpack is a SIGSEGV rather than an arithmetic assertion.
  (Checked: a read one byte past the end faults.) A new consumer phase runs
  `tula_entry_payload_ok` and then the dtype's unpack on every accepted entry.
  **2,003,000 iterations, 40,472 entries unpacked, 0 faults, 0 invariant
  failures.**
- **Byte-for-byte against 1.1.1.** 1.1.1's sources (from git) and 1.1.2's, fed
  identical inputs, produce **identical 2,612,430-byte output**: a 40-tensor file
  with odd padding (unsigned and signed), NF4 pack codes + scales, NF4 unpack,
  int8 quant + dequant, ternary pack + unpack. Every optimization is speed only.
- Gates: `fmt`, `lint`, `vet`, `deny` clean; `doc --check` 0 undocumented;
  `make example` PASS; `make dist` regenerated (no stdlib sidecar needed);
  `deps --verify` 60/60.

## 3. Performance (same machine, same harness, min of 5)

The bench was widened first and run on **unchanged** 1.1.1 code for the
baseline (see [benchmarks](../benchmarks.md)).

| Op | 1.1.1 | 1.1.2 | | Change |
|---|---:|---:|---:|---|
| serialize (100 MB) | 591 MB/s | 4,036 MB/s | **6.8×** | word copy (the stdlib `memcpy` is a byte loop) |
| `tula_find`, 256 long names | 8,860 ns | 766 ns | **11.6×** | query measured once, a longer one rejected up front, 64-bit word compares (`streq` ran `strlen` on both strings per entry) |
| NF4 pack | 6.7 Melem/s | 26 Melem/s | **3.9×** | codebook table + exact early exit in nearest |
| NF4 unpack | 82 Melem/s | 237–248 Melem/s | **3.0×** | per-block scale, table lookup instead of a 16-way compare chain |
| ternary unpack | 155 Melem/s | 373–377 Melem/s | **2.4×** | one load per byte, branchless decode |
| int8 dequant | 350 Melem/s | 416–421 Melem/s | 1.2× | 256-entry table for n ≥ 1024 (on the stack, per call) |
| validate / read (heap) / mmap | — | unchanged | | the real-size check costs nothing measurable |

## 4. External comparison

- **GGUF** (llama.cpp): Cisco Talos reported a series of parser overflows in
  2024, in string/array lengths, key allocation and the tensor-count path
  ([TALOS-2024-1912](https://talosintelligence.com/vulnerability_reports/TALOS-2024-1912),
  CVE-2024-21825, and siblings 1913–1916), and a later integer overflow
  (CVE-2025-53630). tula's manifest is **fixed-width** (48-byte names, 144-byte
  entries) with a capped count, so there are no attacker-sized strings or arrays
  to overflow. That whole class is excluded by construction, and the
  2026-07-01 overflow analysis still holds.
- **safetensors**: Trail of Bits' review found header tensor metadata
  insufficiently validated and the format underspecified
  ([report](https://trailofbits.com/documents/2023-03-eleutherai-huggingface-safetensors-securityreview%20(2).pdf)).
  Careful readers now reject **overlapping tensors, gaps and trailing bytes**,
  and check **shape × dtype == byte length**. tula's `tula_validate` checks
  bounds, not those: overlap, duplicate names, misaligned `data_off` and
  shape/size mismatch all pass. Rejecting them there would break 1.x files the
  1.x writer can produce (the builder allows duplicate names), so the
  strict checks belong in an **additive** validator (roadmap 1.2.0).

## 5. Deferred — need new API (MINOR) or a format decision → roadmap

- **D-1 Long names collide.** The 48-byte name field truncates silently at 47.
  Real names exceed it: Mixtral's `model.layers.0.block_sparse_moe.experts.0.w1.weight`
  is 51, and the LoRA pair `base_model.model.model.layers.0.self_attn.q_proj.lora_A.weight`
  / `…lora_B.weight` truncate to the **same** 47 bytes. For anukulana (the LoRA
  importer) this is a wrong-tensor hazard. Truncation is frozen v1 behaviour; a
  checked add (1.2.0) and a long-name extension (ADR, 1.3.0) are needed.
- **D-2 `TULA_BUILDER_MAX = 256`** is below real checkpoints (Llama-2-7B has 291
  tensors, Mixtral-8x7B ~995). The constant is frozen; a sized builder is
  additive (1.2.0).
- **D-3 Files over 2 GiB.** `tula_serialize` builds the whole file in one
  allocation, and the stdlib caps one at 2 GiB, so no multi-GB checkpoint can be
  written today, and `tula_read_file` can't read one (`tula_open_mmap` can). A
  streaming writer is needed. A *signed* streaming write needs a multi-part
  Ed25519 from sigil, because v1 signs `[0, sig_off)` as one message.
- **D-4 Strict validation** (§4): overlap, gaps, duplicates, alignment,
  shape × dtype == `data_len`, zero unused dims.
- **D-5 Signature stripping.** An unsigned copy of a signed file verifies as
  `UNSIGNED`. Treating that as a failure is the caller's policy today (documented);
  a "signature required" helper makes it one call.
- **D-6 Quant sidecar consistency.** `tula_nf4_unpack` reads `ceil(n / block)`
  scales from the `.scale` sidecar; `tula_entry_payload_ok` on the codes tensor
  does not check that count. Callers must (documented); a pair check is additive.
- **D-7 mmap and concurrent writers.** A mapping is live: another process that
  truncates or rewrites the file after validation can change validated bytes or
  cause SIGBUS. This is inherent to `mmap`; it is now documented on
  `tula_open_mmap`, in `SECURITY.md` and in the guide.
- **D-8** non-atomic `tula_write_file`; **D-9** a heap-read file that fails
  validation keeps its buffer (the bump allocator has no free, so a
  caller-buffer read API helps); **D-10** no F32/F16/BF16 dtypes (most real
  checkpoints are BF16/F16); **D-11** 0-dim entries carry no element count;
  **D-12** the 591 KB smoke binary is mostly bayan's Unicode tables arriving
  via sigil's bundle (sigil's open issue).
