# 0005 — F32, F16 and BF16 dtypes, converted from f64 in integer arithmetic

**Status**: Accepted
**Date**: 2026-11-04

## Context

tula's dtypes were raw f64 and the three quantized codes (int8, ternary, NF4).
Most real checkpoints ship **BF16** or **F16**, and some ship F32. Storing them as
f64 quadruples a BF16 file, and the Type-3 import path (anukulana) needs to keep
the source precision. New `TULA_DT_*` values are additive (a MINOR, STABILITY.md).
`tula_validate` accepts unknown dtypes in every 1.x, so old plain readers still
open such files. 1.2's strict validator rejects them (`TULA_ERR_DTYPE`), which is
right: it can't vouch for a dtype it doesn't know.

What needs deciding is the conversion semantics: rounding, overflow, subnormals,
NaN. The obvious implementation, the hardware conversion (cyrius `f32_from`),
answers those differently depending on the process's floating-point mode: a
flush-to-zero setting turns subnormals into zero.

## Decision

**Add `TULA_DT_F32 = 4`, `TULA_DT_F16 = 5`, `TULA_DT_BF16 = 6`, with conversion
helpers that implement IEEE 754 round-to-nearest-even in integer arithmetic,
straight from f64.**

- **Storage.** `F32` is IEEE binary32 (4 bytes), `F16` IEEE binary16 (2 bytes),
  `BF16` bfloat16, i.e. the top 16 bits of binary32 (2 bytes). All
  little-endian, `data_len = nelems × width`.
- **f64 → narrow** (`tula_f64_to_f32/f16/bf16`, `tula_f32/f16/bf16_pack`):
  - Rounding is to nearest, ties to even, **computed directly from the f64**.
    BF16 and F16 are not rounded through F32, because two roundings can disagree
    with one: 1 + 2⁻⁸ + 2⁻³⁰ is BF16 `0x3F81` directly, but `0x3F80` via F32.
  - Overflow gives ±inf. Underflow gives the correctly rounded subnormal or ±0,
    with no flush to zero. The sign of zero is kept.
  - NaN stays NaN: the sign and the top payload bits are kept, and the quiet bit
    is set. That is the same result as x86 `cvtsd2ss` / aarch64 `fcvt` in the
    default mode, and the F32 path is tested against them.
- **narrow → f64** (`tula_f32/f16/bf16_to_f64`, `…_unpack`) is exact, since
  widening always is. Subnormals are normalized and inf stays inf. NaN keeps its
  sign and payload and comes back **quiet**: IEEE 754 never returns a signaling
  NaN from a conversion, and this matches `cvtss2sd`. (Found by the oracle test:
  keeping signaling NaNs signaling disagreed with the hardware on 572 of 300,000
  random f32 codes, exactly the signaling-NaN share.)
- **Integer arithmetic only**, so a file's bytes never depend on the writer's FP
  mode, and the same input gives the same file on every target.

## Consequences

- **Positive** — BF16/F16 checkpoints are stored at native size, conversions are
  exactly IEEE (exhaustively checked for F16 and BF16: every one of the 65,536
  codes round-trips, and every midpoint between neighbours rounds to the even
  one), and output doesn't depend on the FP environment. `tula_packed_len`,
  `tula_entry_payload_ok` and `tula_validate_strict` learn the sizes, so the
  existing guards cover the new dtypes.
- **Negative** — integer conversion is slower than one hardware instruction (a
  few ns per element; see benchmarks). There is no FP8 yet (E4M3/E5M2 have
  several incompatible NaN/inf conventions, so they get their own decision when
  a consumer needs them).
- **Neutral** — a 1.2 consumer that runs `tula_validate_strict` on a file with
  the new dtypes gets `TULA_ERR_DTYPE` until it upgrades.

## Alternatives considered

- **Hardware conversion (`f32_from` / `f32_to`)** — rejected as the
  implementation because it depends on the FP mode. It is kept as the F32 test
  oracle. There's also no portable hardware path for F16 or BF16 in cyrius.
- **BF16 via F32** (truncate, or the common `+0x7FFF` rounding trick on F32 bits)
  — rejected: it double-rounds f64 input. It is still used in tests as an oracle
  for inputs that are exact in F32, where it is correct.
- **Store narrow floats as f64** — rejected: 2–4× the size, and it loses the
  source dtype.
